# 父子實時推論流程（設計）

> **一句話**：把相機版**已經驗證過**的「環形緩衝＋回頭找」觸發模型搬進 AIVision，
> 中間插入一次父子傳球（子端前處理 → 父端 CRNN 讀字 → 子端拿工單判定）。

---

## 0. 為什麼照相機版

相機版的觸發→存圖流程是**現場實際在跑、而且我們手上所有模號穴號訓練圖都是它拍的**。
它已經解掉三個我原本要問的難題，不需要重新發明：

| 難題 | 相機版的解法 |
|---|---|
| 多幀怎麼取捨 | **不投票**。環形緩衝保留每一幀，觸發後在 800ms 窗內**逐幀回頭找**「完整鏡片正常落在 ROI 內」的那一幀 |
| 沒東西 vs 壞掉 | 兩段式閘門：`probe`（只跑 Hough）先刷掉沒有完整鏡片的幀；過閘門才做完整辨識 |
| 帳對不對得起來 | 停止時檢查 **觸發數 = 存圖 + 逾時放棄 + 待補** |

**AIVision 這邊不缺零件**：`ICameraPort` 已經有 `FrameReceived` 事件與連續擷取迴圈，
環形緩衝不必動相機層。

## 3. 誰做判定：**子端**

父端**不知道工單**，所以它只能回「我讀到什麼」，不能回「過不過」。

```
父端回：「讀到 M17/14，信心 0.97/0.96，模型 b3，門檻 0.90/0.90」
子端做：跟工單的 M108/14 比 → 不一致且信心夠 → MISMATCH → 吹
```

這個分工同時滿足鐵律：**父端掛掉，子端用本機模型讀完照樣判得出來，產線不停。**

## 5. 存檔（決定 1）

一片一組同名檔，`pieceId` 串起來：

```
記錄\2026-08-24\
  ST-01_20260824_000123_raw.jpg      原圖（站端原始）
  ST-01_20260824_000123_strip.png    前處理圖（實際送出的那張）
  ST-01_20260824_000123.json         結果
```

`json` 內容（檔名塞不下這麼多，而且這些是訓練與追溯要用的）：

```
pieceId / 站號 / 時間 / trigTick / 工單 / 工單預期模號穴號
讀值模號穴號 / 兩軸信心 / needsReview / 套用門檻
來源: central | local          ← 這片是父端讀的還是本機接管
模型版本 / 引擎 / 父端耗時 / 端到端耗時
判定: CONFIRM | ACCEPT | MISMATCH | NG
吹氣: 有/無 / 延遲設定值 / 實際觸發→送出間隔
```

**額外好處**：自我強化訓練直接有料 —— 每片都有「圖＋正解＋模型當時怎麼判」，
比現在只在混料時存一張強得多。

**磁碟（決定 1）**：不自動刪。加一個餘量監看：

- 低於 **20 GB** 或 **10%**（取先到者）→ 畫面橘字提示 + log 一次
- 低於 **5 GB** 或 **3%** → 畫面紅字 + 每批提醒一次
- **絕不因為快滿就停止產線或自動刪檔** —— 存不進去只記 log，判定與吹氣照常

> 相機版的存法可以參考：正常件按 `模號\穴號` 分資料夾（訓練資料天然分類好），
> `_MISMATCH` / `_NG` 各自集中。要不要沿用這個分法見 §9。

## 6. 失敗分支（每一條都要有明確去處）

| 情況 | 做什麼 | 吹嗎 | 計入哪 |
|---|---|---|---|
| 窗內找不到完整鏡片 | 放棄該筆 | **不吹** | 擷取失誤（＝重複觸發，要查觸發訊號） |
| 找到鏡片但號沒拍清楚 | 繼續找下一幀 | 不吹 | 不扣帳 |
| 父端逾時 > 100ms / 連不上 | **本機模型接管**，判定照做 | 照判定 | 本機接管 |
| 父端回 4xx | 記 warning，該片本機接管 | 照判定 | 本機接管 |
| 父端回 5xx / 連不上 | 本機接管 **+ 進降級冷卻** | 照判定 | 本機接管 |
| 觸發積壓 > 20 筆 | 洩壓丟棄 | 不吹 | 積壓丟棄 |
| 存圖失敗（磁碟滿/唯讀） | 只記一次 log | 照判定 | — |
| 吹氣送不出去 | 只記 log | — | — |

**帳一定要平**（停止時檢查，不平就在畫面出聲）：

```
觸發次數 = 中央判定 + 本機接管 + 擷取失誤 + 停止時中斷 + 待補
（積壓丟棄另計，不列入觸發數）
```

## 7. ⚠ 100ms 預算的實測疑慮（決定 2）

今天實測的**父端自報耗時**（`serverMs`，不含網路）：

| 批次 | serverMs 分布 |
|---|---|
| 批1（8 張，暖機後） | 42–48 ms |
| 批2（20 張） | 45–194 ms，**其中多筆落在 92–100 ms** |

**100ms 預算會讓相當比例的片子落到本機接管**，而本機是較舊的雙 head 模型
（就是 8/17 掛著的「本機接管準確率」那筆帳）。

**建議**：預算做成**可設定值**（`Devices:InferenceServer:RealtimeBudgetMs`，預設 100），
並在畫面上顯示「本批中央 / 本機」的比例。這樣現場跑一輪就知道 100ms 夠不夠，
不夠往上調到 150/200 即可，不必改程式。

> 決定權仍在你 —— 我照 100ms 做，只是把數字攤開，並讓它可調。

**子端**（產線主頁）
- 觸發數 / 中央判定 / 本機接管 / 擷取失誤 / 待補 —— 五個數字，帳要平

## 11. 建議實作順序

1. **pieceId + trigTick** 貫穿（子端產生、送父端、兩邊都記）—— 沒有它後面全部對不了帳
2. **環形緩衝 + 觸發佇列 + 兩段式閘門**（照相機版；先不接父端，用本機模型驗證帳平不平）
3. **存檔三件套 + 磁碟餘量監看**
4. **接父端**（100ms 預算、逾時本機接管、SRV 燈）
5. **吹氣改用 pieceId 去重 + 記錄實際間隔**
6. 帳平檢查 + 畫面五個數字

> 第 2 步做完就能單獨驗證「觸發模型對不對」，不必等父子傳球 —— 這樣風險是分段的。

## ★ 實作中抓到的三個問題（都已修）

### ⑴ 預算逾時直接取消 HTTP 請求 → **把父端的 sidecar 弄壞**

父端 CRNN sidecar 走 **stdin/stdout 一行一問一答**。請求被中途砍掉時，python 還在處理上一筆，
而我方的 `finally` 已經把暫存圖刪掉 → 下一筆進來時 python 讀到**上一筆已被刪除的路徑**：

```
[InferCrnn] sidecar 失敗：[Errno 2] No such file or directory: ...aivision_crnn_<GUID>.png
```

**實測一次取消污染後面連續 15 筆**，而且比例會隨預算變大而變差（100ms→63%、300ms→25%），
數字反過來遞減就是協定失步的徵兆。

**修法**：預算到了只**停止等待**，**不中止對方**（`Task.WhenAny(call, Task.Delay(budget))`），
讓那個呼叫自己跑完、結果丟掉。代價只是父端多算一張沒人要的圖，還順便讓行程池保持熱。
修後 **36 次推論 0 失敗、0 暫存殘留**。

### ⑵ sidecar 暫存圖放在 `%TEMP%` → 被防毒短暫鎖住

`[Errno 13] Permission denied`，實測 12 次裡失敗 1 次（約 8%）。
**修法**：改放 `<程式目錄>\tmp\crnn\`，並在偵測到檔案存取類錯誤時**換檔名重試一次**。

### ⑶ 一次瞬斷就進 30 秒降級冷卻

8% 的瞬斷會讓整段產線走本機舊模型 —— 與今早在 Route A 修掉的「一件事連坐後面一整批」同一種坑。
**修法**：連續 **3** 次「對方不可用」才進冷卻；成功一次就歸零。逾時**完全不進**冷卻。

另修：閘門原本要求鏡片「完全不超出邊界」，比正式前處理還嚴（它自己會把裁切框夾進影像內），
會把讀得到的片子誤判成擷取失誤 → 加 `LensEdgeTolerance`（半徑的 10%，可設定）。
以及停止時「已記帳又被算成中斷」造成假性帳不平 → 加 `PendingCapture.Counted` 旗標。

## ★★ 父端預算實測：**100ms 太小**

同一台、暖機後、真實影像，各跑 8 片：

| 預算 | 走中央 | 父端自報耗時 |
|---|---|---|
| **100 ms**（原拍板值） | **2/8　25%** | 101–107 ms |
| 150 ms | 5/8　63% | 108–115 ms |
| **200 ms** | **8/8　100%** | 102–190 ms |
| 300 ms | 8/8　100% | 100–188 ms |

**照 100ms 跑，四分之三的片子會落到本機那顆較舊的雙 head。**
建議把 `RealtimeInspection:ServerBudgetMs` 設 **200**（現場可再調，畫面就有中央/本機比例可看）。
⚠ 這是**單站、本機迴路**的數字；跨機加上網路、多站並行搶 GPU 都會更慢，現場要重測。

# 缺口普查（同日，使用者要求「不要現場才發現東西沒備齊」）

我原本只列了三項「還沒做」，那是**沒有系統性掃過**。逐條查完，**又找到六個會在現場咬人的缺口**，全部已補並驗證。

## ⚠ 六個缺口

### ① 前處理參數沒吃設定檔 —— **這個最會咬人**

管線用的是 `new WarpPolarParams()` 的**預設值**：`RoiW = RoiH = 0`，等於**不裁 ROI**。
但產線設定是 `RoiX=240, RoiY=0, RoiW=700, RoiH=680`。

用預設值的話，會拿**整幅相機影像**去找圓 —— 抓到背景/治具的圓、裁到錯的區域，
**讀值全錯，而畫面上一切正常**。這種東西上機才發現就是半天。

修法：從 `MoldCodeWarpPolar:Preprocess` 注入；**閘門、前處理、本機辨識器三者用同一份參數**。
另外啟動時把實際生效的 ROI 與 Hough 半徑**印在畫面上** —— 現場最怕「設定沒吃到卻沒人知道」。

### ② 實時檢測畫面**沒有任何影像**

你問的正是「子端實時畫面」，而那頁 XAML 裡 `<Image>` 數量是 **0**。
現場既看不到相機有沒有在動，也看不到工件有沒有進框。

修法：加相機即時預覽，**並把 ROI 框畫進點陣圖**（不是疊 UI 圖層 —— 畫進圖裡對齊絕不會錯）。
另加「最近一片 原圖 vs 送出的前處理圖」對照，看前處理有沒有裁對。
沒影像時顯示原因，不給一片黑。UI 更新有節流（每幀都轉點陣圖會把 UI 執行緒吃光）。

### ③ pieceId / trigTick **根本沒送給父端**，而且原圖路徑是壞的

設計 §4 寫著「要新增」，我沒做；還把 `pieceId` 塞進了 `rawPath` 欄位
→ 父端「站端原圖位置」欄顯示的是 pieceId 不是路徑，**溯源整條斷掉**，兩邊 log 也對不起來。

更隱蔽的一點：原圖是**最後才存**的，所以送父端的當下 `RawPath` 還是 `null`。

修法：新增 `pieceId` / `trigTick` 兩個 form 欄位（走 form 不走 header——header 只吃 latin-1）；
API、父端最近紀錄、父端畫面都加上 pieceId 欄；**原圖改成送父端之前就落地**。

### ④ IO 觸發**完全沒接** —— 現場按開關不會有任何反應

已驗證的相機版，觸發是讀 **IDS 相機的 `Line0` 數位輸入**（每幀輪詢、上升緣觸發一次），
不是接 PLC。而 AIVision 的 `IdsCameraPort` **一行 Line0 的程式碼都沒有**。

等於整條實時產線**沒有觸發源**，只剩畫面上的手動按鈕。

修法：新增 `ICameraTriggerLinePort`，`IdsCameraPort` 實作（開相機時選 `LineSelector=Line0` 並試讀，
擷取迴圈每幀讀一次 `LineStatus` 判上升緣）；管線訂閱它 → `FireTrigger("IO")`。
線號可設定（`Devices:Camera:TriggerLine`）。**讀不到時畫面紅底明講「按開關不會有反應」**。

### ⑤ 工單要**人工 key**

預期模號/穴號原本是畫面上兩個文字框，沒接工單服務 —— key 錯就是整批誤判／誤吹，
而且與實際工單不同步時**沒有任何地方看得出來**。

修法：加「帶入工單」按鈕，從 `IWorkOrderManagementService` 取目前工單，
拆 `ExpectedMoldCode`（拆法與「工單輸入」頁一致）；畫面標明**預期值是工單帶的還是人工填的**；
**沒有預期值就不准開始**（沒有預期值＝根本沒在檢查）。

### ⑥ 假相機沒擋

相機是 Fake 時，畫面會顯示「運行中、等待觸發」，但永遠不會有幀進緩衝
→ **每次觸發都變成「擷取失誤」**，現場會去查觸發訊號，實際上是相機沒接
（8/19 已經踩過一次同類的坑：`appsettings.Development.json` 把相機蓋成 Fake）。

修法：啟動時擋下並講原因（含「確認沒有載入 appsettings.Development.json」）。

## 驗證：64 項全過（單元 23 ＋ 缺口 10 ＋ E2E 21 ＋ 真父端 10）

- ④ 模擬「現場按開關」→ 觸發一次檢測，帳仍平

# ROI 框（補做，對齊相機版的完整功能）

我原本只在實時檢測頁「把框畫進點陣圖」，那只是相機版功能的一小塊，而且做法也不對。

## 相機版有、我原本沒有的

| | 相機版 | 我原本 |
|---|---|---|
| ROI 存法 | **影像比例 0~1**，與解析度/縮放無關 | appsettings 的**像素**，換相機或改解析度就整個錯位 |
| 畫在哪 | **Canvas 疊層**（同 OCR_demo `viz.draw_live`：永遠畫出送 OCR 的範圍） | 用 OpenCV 畫進點陣圖再重編碼 PNG |
| 拖曳重新框選 | ✅ 拖曳 + 即時座標 + Esc 取消 + 太小自動放棄 | ❌ |
| 重設回預設 | ✅ | ❌ |
| 存檔 | ✅ settings.json，存檔即生效 | ❌ 只能改 appsettings 再重啟 |
| 主頁預覽 | ✅ 一直都畫著 | ❌ 完全沒有 |

**畫進點陣圖那個做法本身也是錯的**：1280×1024 的 PNG 編碼一次要 10~30ms，
每顯示一幀就付一次；而且畫進圖裡就沒辦法做拖曳框選。

## 現在的做法

**`Services/RoiSettings.cs`** —— ROI 一律存**比例**，放 `configs/roi.json`：

- 比例 → 像素在使用時才換算（`ToPixels`），所以**換相機、改解析度、改 Binning 都不會跑掉**
- 放 `configs/` 不放 appsettings：ROI 是**現場校正值**，要在機台上邊看邊拖、存檔即生效；
  appsettings 是部署設定，改它要重啟而且 rebuild 會被蓋掉（同 `blow.json`／`camera-ids.json` 的作法）
- **第一次執行自動搬家**：沒有 `roi.json` 時，用 appsettings 既有的像素 ROI 換算成比例並存檔 ——
  現場不必手動重設，也不會突然變成「沒有 ROI」

**`Views/Controls/RoiPreview.xaml`** —— 影像 + ROI 疊層的共用控制項：

- **框永遠畫出來**，那就是送去辨識的範圍
- **拖曳重新框選**：拖的時候就顯示換算後的像素座標（放開才知道框到哪太慢）；
  Esc 取消；**小於 50×50 自動放棄**（多半是誤觸點一下就放開，直接套用會讓 ROI 變成一個小點、整條產線讀不到東西）
- 座標基準一律用 `ViewHost`（Grid）——`Canvas.ActualWidth` 在某些機器/時序會回 0，
  造成除以零、ROI 消失或框選失效（相機版踩過這個）

**接到哪兩個畫面**

- **模號穴號實時檢測頁**：完整功能
- **主頁預覽**：**同樣是完整功能**（見下節「8/25 補：自訂 ROI 與功能歸位」）

**框選完立刻生效**：`RoiSettings.Changed` → 管線自己重算成當下幀尺寸的像素 →
閘門與前處理同時換。**畫面畫的框 = 實際判定的區**，不會有兩套。

## 驗證：ROI 16 項（總計 80 項全過）

| 驗什麼 | 結果 |
|---|---|
| 同解析度設多少回多少 | 240,0,700×680 ✔ |
| **解析度翻倍 → ROI 跟著翻倍** | 480,0,1400×1360 ✔（這就是存比例的意義） |
| 解析度減半 → 跟著減半 | 120,0,350×340 ✔ |
| 存檔 / 重新載入往返一致 | ✔ |

| 超出邊界會夾在影像內 | ✔ |
| 沒有 roi.json 時從 appsettings **搬家**並存檔 | ✔ |

| 變更會發事件（畫面與管線同步） | ✔ |

### 測試自己說謊的那一次（第 4 次了）

前三項一開始是紅的。原因不是程式壞，是**測試執行緒沒有訊息迴圈** ——
`RoiSettings.Changed` 可能來自相機執行緒，所以重畫是 `BeginInvoke` 排進佇列的，
不催就永遠不執行。補了 `Pump()`（等同 DoEvents）之後全過。

**教訓同 8/24**：紅燈先問「是程式錯，還是我的量法錯」。
