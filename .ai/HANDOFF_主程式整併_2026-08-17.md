## 2. ★核心定案（不要再反覆）

### ① `is_strip`：父端只做辨識
**曾卡整晚**：站端送檢讀值全空、server 回「未偵測到鏡片」。
**根因**：父端 `CrnnEngine.predict()` 是**全包式**（不管誰送來都先找圓+展開），站端已前處理的 strip 再被找一次圓當然失敗。
**使用者一句話點破**：「誰叫你把已做過前處理的再做一次？**只有子節點做前處理、父節點做辨識**」。
**修法**（全部向後相容，預設 false）：

| # | 檔案 | 改動 |
|---|---|---|
| ① | `D:\OCR_demo\app\ocr\crnn_engine.py` | `predict(..., is_strip=False)`；true 就跳過找圓/展開 |
| ② | `D:\OCR_demo\app\serve.py` | 把 `is_strip` 傳進 predict |
| ③ | `AIVision.Api/Services/CrnnSidecarService.cs` | 送 python 的 JSON 帶 `is_strip` |
| ④ | `AIVision.Api/Controllers/CrnnInferController.cs` | 表單加 `IsStrip` 欄位 |
| ⑤ | `AIVision.Infrastructure/MoldCode/CrnnInferClient.cs` | client 可帶 `isStrip` |
| ⑥ | `RouteAEdgeViewModel.cs` | **前處理成功才標記**（找不到圓退回送原圖時不標） |

> ⚠ **①② 是使用者的 python，動前已備份** `crnn_engine.py.bak_20260817`、`serve.py.bak_20260817`。

### ② 本機接管（使用者提議）
「有本地模型可以自己接管，過一陣子再問中央，沒斷就切回去」。
- 原本「本機備援」只標記 `(local)` **沒有實際辨識** → 改為注入既有 **`IMoldCodePairRecognizerPort`（雙 head ONNX）真正接管**。
- **30 秒冷卻**：中央掉線後期間不重試（原本每張空等 TCP 逾時 ~4100ms，30 張跑 2 分鐘）→ 改後**第 1 張 4117ms，其餘全 0ms**。
- 冷卻期滿自動再試，通了狀態列提示「中央推論已恢復，切回中央辨識」。

### ③ 三種送法只有一種可行（已實測）
| 送法 | 讀值 | 傳輸量 |
|---|---|---|
| **strip（完整前處理下放）** | ✅ 30/30 | ✅ **−68.7%** |
| crop（只裁圓不展開） | 3/4 | ❌ **+271%**（JPEG 裁出存 PNG 更大） |
| raw（原圖直送） | ❌ HTTP 415 | 0%（端點只收 PNG） |

## 7. 踩坑 / 工作紀律

- **父端不該重做前處理**（架構原則，見 §2①）——這是本階段最大教訓。
- WPF：**`Background` 直接寫在元素上會壓過 Style Trigger** → disabled 灰色失效。要寫在 `Style` 的 Setter 內。
- **測試要涵蓋真實情境**：POC 那次是中文路徑、這次是「已前處理的圖」——**開發機順順的不代表現場會過**。
- 連線判斷**一律 `Test-NetConnection -Port`，不要用 ping**（防火牆常擋 ICMP）。
- **手機熱點會隔離裝置**，不能當兩機的橋。
- 建置前先關掉正在執行的 App（否則 exe 被鎖 MSB3027）。
- 動使用者的 python 前**先備份**。
- 每次動 `.ai` 要同步 `status.json` + 跑 `python D:\專案管理\process\build_dashboard.py`。
