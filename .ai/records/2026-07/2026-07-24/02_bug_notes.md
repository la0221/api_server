# Bug Notes - 2026-07-24

## 坑 1：驗收按鈕「健檢 ✅ 但推論必逾時」— 逾時預算照「最佳量測值」訂，卻沒對齊「實際部署設定」

### 1. 情境

使用者第一次實測驗收按鈕（M83 圖，727×593）：健康檢查 8ms ✅，推論卻回 `❌ 中央推論逾時 (>350ms)`。

### 2. 根因（自己造成的設定矛盾）

- `InferenceServerOptions.TimeoutMs=350` 是照 **Passes=1 的量測值（191ms、p90 209ms）** 訂的（要 < 400ms 節拍）。
- 但 server 端**保守維持 Passes=2**（未大樣本驗證前不改預設）→ 單張實測 **317-326ms、來回 387-463ms**，冷啟首張可達 1.1s。
- 350ms 逾時 vs 實際 ~400ms 來回 → **必逾時**。健檢會過（不跑推論、8ms），更顯得「路通了卻壞」。
- 兩個「各自正確的保守決定」（逾時抓緊、Passes 抓穩）疊在一起變成矛盾——**沒有人回頭對齊**。

### 3. 解法

- 試模/驗收期逾時調成 **2000ms**（appsettings + options 預設 + 註解寫明兩情境）。
- **試模逾時與生產逾時是兩回事**：試模要寬（別擋住測試）；生產實時（階段 3 之後）必須 < 節拍（如 350）才來得及降級——屆時分開設定，勿共用一個值。
- 用同一張 M83 圖在 HTTP 層重現驗證：3 次皆成功（server 317-326ms、來回 387-463ms < 2000ms）。

### 4. 下次遇到類似問題，AI 應先檢查

- **逾時/預算類參數要對齊「實際部署的設定」，不是「最佳量測值」**。量測時是什麼組態（Passes/Build/硬體），逾時就照那個組態訂；組態改了要回頭改逾時。
- 「健檢過、業務呼叫必失敗」的形狀 → 先懷疑**兩者的資源/耗時特性不同**（健檢不跑推論），別急著查網路。
- 一個 client 參數服務多種情境（測試 vs 生產）時，**先問要不要拆成兩個參數**。

## 觀察 2（非 bug，試模發現）：v671 baseline 在 M83 上讀錯 → M58（conf 0.596）

- 同張 M83 圖：穴號 01 讀對（conf ~1.0），**模號讀成 M58、信心僅 0.596**。
- **不是字集問題**：查 v671 mohao.onnx metadata，字集 20 類**含 M83**（M101/M15/M17/M23/M28/M49/M50/M52/M53/M54/M56/M58/M59/M60/M61/M82/M83/M95/M96/NG）。
- 是模型在該模號（至少該張圖）上弱。**門檻保護有效**：0.596 < 生產模號門檻 0.60 → 三態判定不會採信（fail-closed 如設計運作）。
- n=1 不下結論 → 正確動作是用**批量試模（來源=中央伺服器）**跑整個 M83 資料夾看命中率——這正是「跨模號大樣本驗證」缺口的實例，也正是隔離試模功能的用途。
