# Reusable Flow - 2026-07-16

## Flow 1：把新的遠端能力「零風險」接進既有生產 App

### 觸發情境

既有 App 的某能力（本案：雙 head 辨識）跑得好好的，要新增一條「走遠端 server」的路，但**不能冒險影響生產**。

### 流程步驟

1. **前置：server 補健康檢查端點**（不送資料、不做重運算的輕量探測）。任何連線示意/燈號都需要它；且要能分辨「連不上」vs「活著但沒就緒」——**兩者都回 200**，用 `status` 欄位區分，讓 client 自己判該不該降級。
2. **新增遠端適配器，實作同一個 port**，但**先不綁 port**。DI 只註冊具體型別 → 生產路徑（綁在 port 上的本機實作）**完全不受影響**。
3. **加「測試/驗收」按鈕**，以**具體型別**注入遠端適配器。此時：路通不通看得見，但生產辨識一行都沒改 → **零風險**。
4. **驗收通過後**才加來源選擇器（包兩個 port 實例）接管 port；再往後才上自動降級。
5. 設定預設 **`Enabled=false`**，導入期生產照舊。

> **關鍵心法**：「**先證明路通，再談切換**」。把「新能力可用」與「新能力接管」拆成兩步，中間有個看得見的驗收點。

### 為什麼有效

- 階段 2 的按鈕是**唯一**使用遠端適配器的地方，且它不在熱迴圈 → 出錯最多是按鈕顯示失敗。
- 使用者能**親眼看到**打通（不是「我說它通了」），對導入信心與除錯都有價值。

## Flow 2：接既有 UI 前，先派探查代理「盤點現有慣例」

### 觸發情境

要在一個成熟 App 加新 UI（狀態燈/面板/按鈕），但不知道專案既有做法。

### 流程步驟

派一個唯讀探查代理，明確問這幾類問題（本案實證有效）：
1. **Shell/主視窗結構** —— 全域狀態放哪？
2. **既有的同類元件** —— 有沒有現成的燈號/badge？用什麼手法（Ellipse+Brush？Converter？DataTrigger？）
3. **同類資料顯示在哪** —— 結果/版本/來源怎麼呈現？
4. **既有的「切換/選擇」範式** —— 選→commit→回報 的既有流程長怎樣？
5. **事件/訊息機制** —— Messenger 還是 C# event？現有型別有哪些？
6. **DI 註冊慣例** —— HttpClient/Options 怎麼註冊？

要求回報**檔案路徑+行號+程式碼片段**，重點是「現有慣例長什麼樣」。

### 本次收穫（沒探查就會踩的）

- Shell 燈號**不用 Converter**，而是 VM 直接暴露 `Brush` 屬性 → 若自創 Converter 就與全案不一致。
- 硬體狀態走 **C# event 而非 Messenger** → 若用 Messenger 就違反慣例。
- 已有 `NullToVisibilityConverter`（且**已處理空字串**）→ 我原本要自創 `NullToCollapsedConverter`，白做。
- `AinaviOptions` 是**硬編 Host 的反面教材**，該學的是 `Configure<T>(GetSection)` → 探查讓我知道「哪個慣例該學、哪個不該學」。

### 可否變成 Prompt / SOP？

- Prompt：**yes**（上面六問可直接當探查提示模板）。
- SOP：**yes**（每次要接既有 App 的 UI 都該先跑一輪）。
- Skill：no（屬判讀，不需工具化）。
