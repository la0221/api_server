# Q1 網路延遲測試結果

> 前一場只量了「算力」（多執行緒）。這場**經真 HTTP、經父子節點**跑真 OCR，把「傳輸/網路延遲」補進來。
> 方法：子端 `--bench` 送 150 張給父端(真 CRNN)，量**端到端來回**；再用 `--sim-net-ms` 疊加模擬網路延遲。

## 1. 實測數字（端到端 p50，含 HTTP + 推論）

| 情境 | 1 緒 e2e p50 | 父端純推論 | **傳輸/網路開銷** | 1 緒 rps | 4 緒 rps |
|---|---|---|---|---|---|
| **C** localhost（同機/有線同網段近似） | 37.8ms | 37.2ms | **≈0.6ms** | 21.7 | 46.0 |
| **D** +5ms 模擬（有線 LAN 級） | 45.0ms | 39.1ms | ≈6ms | 21.8 | 44.2 |
| **E** +30ms 模擬（WiFi / 跨網段級） | 86.2ms | ~55ms | ≈30ms | 12.1 | 42.5 |

## 2. 四個結論

1. **有線同網段：HTTP 傳輸幾乎免費（≈0.6–1ms）** → 端到端 ≈ 純推論（OCR ~38ms）。**網路不是瓶頸**；前一場的算力數字（OCR 54ms、母模 136ms）基本上就是有線 LAN 的真端到端。

2. **網路延遲直接加在「單張延遲」上**（+5ms→+5、+30ms→+30）。單站看 = 直接吃**節拍餘裕**。WiFi/跨網段的 30ms 會讓每張多 30ms。

3. **但「吞吐」可被併發藏住**：1 緒時 +30ms 把吞吐砍半（21.7→12.1 rps）；**4 緒時吞吐回到 ~42 rps**（多個請求在途，網路等待互相重疊）。→ 多站要**吞吐**時，網路延遲影響比想像小（只要 pipeline）；但要**單張低延遲**時，網路是直接的加項。

4. **吞吐天花板（~46 rps）不論「純算力」或「經 HTTP」都一樣** → 再次證明**瓶頸是算力（GPU/串行），不是傳輸**。HTTP + 網路是次要。

## 3. 對多站架構的建議

- **產線走有線**（GigE 同網段）：網路延遲可忽略（~1ms），端到端 ≈ 純推論。**別用 WiFi**（30ms + 抖動 p99 才是風險）。
- **單站節拍緊**時：把網路壓到最低（有線、同網段、keep-alive、關 Nagle——POC 都做了）。
- **多站要吞吐**時：靠併發把網路等待藏起來（pipeline 重疊）＋ 解算力瓶頸（P-B GPU、P-C session 池）。**真正的天花板還是算力，不是網路。**
- ⚠ p99/max 偶有尖峰（本測 max 到 ~965ms）＝首請求冷啟/GC；生產要暖機 + fail-closed 兜底（server 慢就走 edge 本機後援，不停線）。

## 4. 一句話

**在有線區網上，HTTP 傳輸幾乎不花時間（~1ms），端到端 ≈ 純推論；網路延遲會加在單張延遲上、但可被併發藏住；瓶頸自始至終是算力不是傳輸。** 父子節點通訊已打通，可作為多站的最小骨架。
