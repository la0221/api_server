## 3. ★根因分析：害整天卡關的真兇 —— HTTP header 塞了中文路徑

**現象**：子端跑 Route A，每張都 `LOCAL-FB`、`server-ok=0`，且 `e2e` 只有 1–16 ms（瞬間失敗，不是逾時）。父端 log 完全沒有對應紀錄。

**誤導性極強的旁證**（一度把方向帶往網路/防火牆）：
- `child_edge.exe` 送原圖 → **成功**（同一台機、同一個 IP 與埠）。
- 驗證機**瀏覽器**開 `http://192.168.0.221:8770/recv` → **成功**。
- `python -c "socket.create_connection(...)"` → **PYTHON OK**。
- 父端 `GET /health` → 200 OK。

**真因**：`route_a_edge.py` 為了溯源，把「原圖在子端的完整路徑」放進 HTTP header `X-Raw-Path`。**HTTP header 只能用 latin-1**，而子機路徑含中文（`…\POC_latest\父子節點POC\…`）→ `http.client` 在**送出前**就丟
`UnicodeEncodeError: 'latin-1' codec can't encode characters` → **封包從未離開子機**。

- `child_edge.exe` 不送這個 header，所以不受影響 → 造成「exe 可以、python 不行」的假象。
- 開發機測試一路都用 `/tmp`、`C:\Users\User\AppData\Local\Temp\...` 等**純英文路徑**，完美錯過此 bug。

**修法**（`common.py`）：新增 `header_safe()`，所有 header 值（含 `X-Station-Id`/`X-Task`/`extra_headers`）非 latin-1 一律 percent-encode；父端 `parent_server.py` 以 `unquote()` 還原顯示。
**驗證**：在**含中文的輸出路徑**下重跑 → `server-ok=3`、讀值全對；子機實跑 → **30/30**。

> **教訓（已寫入工作紀律）**：
> 1. **任何進 HTTP header 的值都必須 ASCII/latin-1 安全**，路徑、檔名尤其危險。
> 2. **測試必須涵蓋「含中文路徑」的情境** —— 只用英文路徑測，等於沒測到現場。
> 3. 失敗時**必須把真正的例外訊息印出來**。原本畫面只顯示 `(local)`，把所有人導向網路排查；補上「↳ 送不到父端的原因：…」後，5 秒定位。
