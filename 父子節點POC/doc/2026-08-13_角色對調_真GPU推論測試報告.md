# 角色對調 — 真 GPU 推論測試報告

## 摘要（先看這段）

第一輪測試（見 `2026-08-13_跨機測試報告_lh-dmz.md`）以 Linux 為父機，因該機無 torch／模型，**T5 真 GPU 推論被迫跳過**。本輪將角色對調——**Windows 開發機當父（server），Linux 當子（edge）**——因為 GPU、`lens-gpu` 環境與 CRNN 權重全都在 Windows 這台，對調後 T5 才可能執行。

三項結論：

1. **T5 Pass。** 跨機真推論閉環成立，**讀值 37/37 全對**（含一張舊版誤讀的案例，v3 權重讀對）。
2. **🔴 量到單卡算力天花板：一顆 RTX 3050 約 18 張/秒，且併發完全無效。** 加併發只會惡化延遲，吞吐一張都不會多。這實證了設計書「session 池解串行」的必要性。
3. **⚠ 本輪跨機數字含約 30 ms 的量測裝置偏差**（SSH 反向隧道 `-R` 特有，正向 `-L` 沒有）。引用數字時務必扣除，詳見 §5。

### 為什麼用反向隧道

角色對調後連線方向也反了：需由 **Linux 主動連入 Windows**。但 Linux 在 `192.168.10.x`、Windows 在 `192.168.1.x`，中間隔 FortiGate，**inbound 不通**。

SSH 反向隧道由 **Windows 主動向外**建立 SSH 連線（outbound 可通），在 lh-dmz 上開一個 `127.0.0.1:8775` 的監聽轉回 Windows，**不需任何 inbound 放行、不需改防火牆**。因 OpenSSH 預設 `GatewayPorts no`，該埠只綁 loopback，**僅已登入 lh-dmz 者可存取**，DMZ 網段與公網皆不可達。避開 8770 是因該埠已被使用者既有的父端行程佔用。

> 本輪代價是引入了約 30 ms 的隧道開銷（§5），這是選擇 `-R` 的已知成本。

### 3.2 🔴 純 GPU 算力天花板（本機 loopback，無隧道，已暖機）

**這是本輪最重要的數據**，因為完全不含網路與隧道汙染：

| conc | ok | err | **rps** | p50 | p90 | p99 | max | server-ms(p50) |
|---|---|---|---|---|---|---|---|---|
| 1 | 30 | 0 | **18.3** | 52.0 | 57.9 | 121.9 | 121.9 | 50.9 |
| 2 | 30 | 0 | **17.3** | 106.8 | 128.5 | 283.8 | 283.8 | 105.3 |
| 4 | 30 | 0 | **17.6** | 176.1 | 423.6 | 623.5 | 623.5 | 174.4 |

兩個現象同時出現，指向同一件事：

- **rps 從頭到尾平在 17–18**，併發 1→2→4 完全沒有提升。
- **`server-ms` 隨併發等比放大**：50.9 → 105.3 → 174.4，比值約 ×1／×2.07／×3.43。

`server-ms` 只計 `ENGINE.infer()` 的耗時。它隨併發等比放大，代表**請求在 `infer()` 內部就被排隊序列化了**——不是網路、不是 HTTP 層，是推論本身一張一張做。

**結論：對單一 GPU 加併發，只換到延遲惡化，吞吐一張都不會多。** conc 4 時 p99 衝到 623 ms，而 rps 增益為零。

## 5. ⚠ 量測裝置偏差：反向隧道 `-R` 的固定開銷

跨機真推論 conc 1 的 `p50 − server-ms` 約 30 ms，與第一輪修正後測得的 4.3 ms 明顯不符。為釐清是程式問題、網路問題還是量測裝置問題，改用 **stub 父端**（`server-ms` 恆為 54.5，相減才乾淨）走**同一條反向隧道**：

```
conc     ok   err      rps     p50     p90     p99     max  server-ms(p50)
   1     30     0     11.5    86.9   103.3   140.1   140.1      54.5
   2     30     0     20.9    89.0   135.1   166.2   166.2      54.5
   4     30     0     36.5   103.1   155.8   157.4   157.4      54.5
```

決定性對照——**同一支修正後的程式、同樣 100 KB 影像**：

| 隧道方向 | 傳輸成本 |
|---|---|
| 正向 `-L`（第一輪） | **4.3 ms** |
| 反向 `-R`（本輪） | **32.4 ms** |

**結論：那 30 ms 是 SSH 反向隧道 `-R` 特有的固定開銷，與 `parent_server.py`、與實體網路都無關。**

因此：

- 本輪所有跨機 e2e 數字（如 conc 1 的 104 ms）**應扣除約 30 ms** 才接近真實。
- 修正後跨機單張真實 e2e 推估 ≈ **78 ms**（約 74 ms 推論 + 約 4 ms 網路）。
- **`server-ms` 不受影響**（它在父端內部量測），故 §3.2 的算力結論完全不受此偏差影響。
- 此偏差的根本成因**未進一步追查**，僅定位到「`-R` 有、`-L` 沒有」。

## 6. 決策意涵

### 6.1 算力規劃

- **一台 RTX 3050 的服務上限 ≈ 18 張/秒**（硬天花板）。若每站每秒 1 張，理論約 18 站；實務建議抓 **10–12 站**留餘裕。
- **A1000 等其他卡需另行量測**，不可用本數字外推。
- 結合第一輪結論（網路傳輸僅約 4 ms、且 stub 下吞吐隨併發近線性）：**傳輸極便宜、算力是唯一瓶頸**，故拓撲應採「少數 PC 集中收多站」，把預算放在 GPU 而非每站一台 PC。

### 6.2 edge 端設計

- **不要用多執行緒併發打同一個 GPU 父端。** 併發 4 相比併發 1：吞吐 0 增益、p99 從 122 ms 惡化到 623 ms。
- 邊緣端應**排隊循序送**，延遲反而最低（52 ms）。
- 真正能解序列化的是 **batch 化**或**多 GPU／多行程**，不是客戶端加併發。

### 6.3 量測方法

- **明天量真 GPU 前務必先空跑 3–5 張暖機**，否則首張的 1.6 秒會嚴重拉歪平均值。
- 比較不同輪次的數字時，**須確保暖機條件一致**。
- 要取得嚴謹的跨機真推論延遲，應使用**正向隧道 `-L`**（父端在對面）或**直連**，避免 `-R` 的 30 ms 偏差。

## 7. 待辦與風險

- [ ] **執行緒安全疑慮（建議查證）**：`parent_server.py` 使用 `ThreadingHTTPServer`，多執行緒共用**同一個** `ENGINE` 實例，`OcrEngine.infer()` 直接呼叫 `self.reader.read()` **未加鎖**。本次併發測試結果全部正確，但從多個 Python 執行緒併發操作同一個 torch 模型並無安全保證。既然 §3.2 已證明併發對吞吐毫無幫助，**建議直接在父端序列化處理（加鎖或改單執行緒 + 佇列）**，既消除風險又不損失吞吐。
- [ ] 於 A1000 或目標產線 GPU 重複 §3.2 的量測，取得該卡的實際天花板。
- [ ] 評估 batch 推論可行性——這是唯一能突破 18 張/秒的方向。
- [ ] 重編 `parent_server.exe`（第一輪報告待辦，仍未完成；現有 exe 內含未修正的 Nagle 缺陷）。
- [ ] 若需嚴謹跨機真推論數字，改用 `-L` 或直連重測。

## 8. 本輪效度邊界（誠實揭露）

1. **`-R` 隧道 30 ms 偏差**（§5）：所有跨機 e2e 數字受影響；`server-ms` 與算力結論不受影響。
2. **樣本數 30**：`--n 30`，故 p99 的索引即等於最大值（可見多列 p99 與 max 完全相同），**p99 在此無統計意義**。
3. **單一 GPU 型號**：結論僅適用 RTX 3050 Laptop，不可外推至其他卡。
4. **序列化的確切成因未隔離**：已確認請求在 `infer()` 內被序列化，但未區分是 CUDA 本身、Python GIL、或模型物件共用所致。對「併發無用」的結論不影響，但若要突破天花板需先查清。
5. **`-R` 偏差的根因未追查**：僅定位到方向差異。
6. **僅測 ocr 引擎**：`--engine lens`（母模鏡片偵測）本輪未測。
7. **未測 Route A（T4）**：本輪與第一輪皆未執行。
