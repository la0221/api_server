# 父子節點跨機測試報告 — lh-dmz（Linux 父機）

## 摘要（先看這段）

在**真實跨機、跨網段**條件下完成 T1（純傳輸延遲）、T2（併發吞吐）、T3（網路穩定度）三項主菜，**全數 Pass**。

但探路階段就發現一項**父端程式缺陷**：`parent_server.py` 的 HTTP Handler 未關閉 Nagle 演算法，導致**每筆請求固定多出約 40 ms**。此缺陷在本機 loopback 測試下不會顯現，因此躲過了 2026-08-12 的 8 支 bat acceptance。

修正前後對照（100 KB 影像、單一併發）：

| | 端到端 p50 | 扣掉父端 54ms 後的傳輸成本 |
|---|---|---|
| 原版父端 | 99.3 ms | **45.2 ms** |
| 關 Nagle 後 | 58.8 ms | **4.7 ms** |

**結論：真實網路傳輸極便宜（單張 100KB 圖約 4 ms），瓶頸在算力而非傳輸。** 拓撲可採「少數 PC 集中收多站」。

⚠ **但若不修此缺陷，明天現場量到的每個數字都會虛高 40 ms，並可能導向「傳輸很貴、必須每站一台 PC」的錯誤拓撲結論。**

## 3. 測試方法

為了能把「真網路成本」從「軟體開銷」和「隧道開銷」中分離出來，設置三條可對照的路徑：

| 路徑 | 說明 | 用途 |
|---|---|---|
| **A** | 子機 →（SSH 隧道）→ lh-dmz **原版**父端 | 主測項 |
| **B** | 子機 → 本機 loopback Windows 父端（port 8771） | **基準**：純軟體開銷，不含任何網路 |
| **C** | 子機 →（SSH 隧道）→ lh-dmz **關 Nagle** 父端（port 8779） | 對照：驗證缺陷歸因 |

A 與 C 走**完全相同的隧道機制**，唯一差異是父端是否關閉 Nagle，故兩者差值可直接歸因於該設定。

## 4. 測試結果

### 4.1 基準：本機 loopback（路徑 B）

```
conc     ok   err      rps     p50     p90     p99     max  server-ms(p50)
   1     20     0     17.9    55.5    56.3    62.5    62.5      54.6
```

軟體開銷 = 55.5 − 54.6 = **0.9 ms**，與文件所述「loopback 約 1 ms 軟體開銷」完全吻合。**證明量測工具本身準確**。

### 4.2 首輪探路：路徑 A 出現異常

```
conc     ok   err      rps     p50     p90     p99     max  server-ms(p50)
   1     20     0     10.2    99.6   100.7   101.3   101.3      54.1
```

20/20 成功、err = 0，**功能面完全打通**。但傳輸成本 = 99.6 − 54.1 = **45.5 ms**，而實測 TCP RTT 僅約 2 ms，兩者相差逾 20 倍，數字不合理。40 ms 這個量級是 delayed-ACK 的典型指紋，故展開追查。

### 4.3 排除頻寬因素：payload 大小掃描

若成本來自頻寬，應隨 payload 線性上升。實測：

| payload | 路徑 B（loopback）傳輸 | 路徑 A（隧道，原版）傳輸 |
|---|---|---|
| 1 KB | 0.7 ms | 44.3 ms |
| 10 KB | 0.8 ms | 43.2 ms |
| 50 KB | 0.9 ms | 44.7 ms |
| 100 KB | 0.9 ms | 45.0 ms |
| 200 KB | 1.0 ms | 46.3 ms |
| 400 KB | 1.0 ms | 48.8 ms |

**1 KB 與 400 KB 的成本幾乎相同（44.3 → 48.8 ms）**。payload 放大 400 倍，成本只增加 4.5 ms。這排除了頻寬與影像大小的可能，指向**每次來回一個固定的延遲底噪**。

### 4.4 定因：關閉 Nagle 對照（路徑 C）

複製一份父端，**僅增加一行** `disable_nagle_algorithm = True`，走同一條隧道重測：

| payload | A 原版 | C 關 Nagle | 差異 |
|---|---|---|---|
| 1 KB | 43.7 ms | **3.0 ms** | −40.7 ms |
| 100 KB | 45.1 ms | **4.3 ms** | −40.8 ms |
| 400 KB | 48.3 ms | **8.3 ms** | −40.0 ms |

三種 payload 一致減少約 **40 ms**，歸因明確。

修正後的數字也**內部自洽**：1 KB 的 3.0 ms ≈ 實測 TCP RTT 2 ms + 約 1 ms 隧道／加密開銷；400 KB 增至 8.3 ms 才開始呈現合理的頻寬效應。

## 5. 根因分析

**位置**：`parent_server.py` 第 111–112 行，`Handler(BaseHTTPRequestHandler)` 類別定義。

```python
class Handler(BaseHTTPRequestHandler):
    protocol_version = "HTTP/1.1"       # 支援 keep-alive
    # ← 缺少 disable_nagle_algorithm = True
```

**機制**：Python 標準庫的 `BaseHTTPRequestHandler` 其類別屬性 `disable_nagle_algorithm` **預設為 `False`**，即 Nagle 演算法為開啟狀態。父端回應時，`send_response()` / `send_header()` / `end_headers()` 與 `wfile.write(body)` 會產生多次寫入；Nagle 會壓住後續小段、等待前一段的 ACK，而對端採 delayed ACK（Linux 預設約 40 ms），於是每次回應固定卡一個 delayed-ACK 週期。

**為何一直沒被發現**：

1. **子端有做、父端沒做。** `common.py:35` 的 `Client._connect()` 明確設定了 `TCP_NODELAY`，`README.md` 因此聲稱「HTTP 注意事項已落實：keep-alive 連線重用、關 Nagle(TCP_NODELAY)、逾時」——但該項**僅子端落實，父端遺漏**。
2. **loopback 不觸發。** 環回介面不會產生 delayed-ACK stall（見 4.3 路徑 B 全部落在 1 ms 內）。2026-08-12 的 acceptance 全程在本機進行，因此 8 支 bat 全 PASS 卻仍帶著此缺陷。**這正是跨機測試的價值所在。**

**修正**：

```python
class Handler(BaseHTTPRequestHandler):
    protocol_version = "HTTP/1.1"       # 支援 keep-alive
    disable_nagle_algorithm = True      # 關 Nagle，避免 delayed-ACK 造成每筆 +40ms
```

## 8. 本次測試的效度邊界（誠實揭露）

以下事項限制了本報告數字的適用範圍，引用時請一併考量：

1. **SSH 隧道並非裸連線。** 所有數字都含約 1 ms 的 SSH 加密與轉發開銷（由 3.0 ms 傳輸成本減去實測 2 ms TCP RTT 推得）。真實裸連線會**略優於**本報告數字。
2. **跨網段經 FortiGate。** 路徑為 `192.168.1.x → FortiGate → 公網IP → 192.168.10.x`，比同網段直連多一段繞送。這也是真網路 3–4 ms 略高於文件預期 0.5–3 ms 的合理解釋。
3. **樣本數偏小。** `--n 150` 但 `sample_images/` 僅 30 張，故每輪實際為 30 筆。n=30 時 p99 的索引即等於最大值（可見 conc 1 兩組的 p99 與 max 完全相同），**p99 在此實質上只是最大值，統計意義有限**。若要嚴謹的尾端延遲數據，需擴充影像數量或增加 `--n` 的重複輪次。
4. **T2 併發僅測到 conc 4。** 在此規模下未觀察到隧道多工瓶頸，但不保證更高併發下仍然成立。
5. **未涵蓋 T4／T5／T6。** Route A 資料流、真 GPU 推論、Demo 展示本次均未執行。
6. **WiFi 對照組未做。** 全程走有線路徑。
